Overview

Background

At Walker's Doughnuts, the things that made a shift run well were rarely written down. A manager knew how to handle a rush, and a senior staff member knew the fastest way to prep for the morning, and none of it survived when that person wasn't rostered on. Around the same time, our store slid from one of the better performers in the franchise toward the bottom of the leaderboard, and staff turnover was high. I can't say the ranking drop was caused solely by knowledge loss, but I saw first-hand how much operational knowledge disappeared every time someone left.

Problem

Operational knowledge, standards, training, and workflows fragment across locations and staff, and disappear when someone leaves.

Solution

A shared operations platform for tasks, scheduling, procedures, tools, and staff coordination, captured once, reused by every shift.

Why I built it

“The success of one location should strengthen every location.” I didn't set out to build a SaaS product. I set out to fix this at one store, and FriendChise is still running that store today.

Product

Product overview

Timetable, tasks, procedures, and tools are built as separate systems sharing one org-scoped data layer, so screenshots below reflect what a real shift actually sees.

Run the week

Weekly and daily scheduling so staff know what they're doing without asking a manager. Overlapping shifts and roles are grouped into readable cards instead of a wall of stacked entries, which removes the constant "what am I doing today" interruptions that used to eat into a manager's time.

Standardise operational knowledge

Recurring tasks, prep procedures, and recipes that used to exist only on paper or in someone's head are written once and searchable by anyone on shift. Tags, comments, and recurrence rules turn a scrap of tribal knowledge into something the whole team can trust.

Train and support staff

Conversion tools, operational calculators, and item lists remove repetitive manual math from day-to-day work, the kind of thing that seems minor until you're the one doing it by hand every shift, and a big part of onboarding someone new quickly.

Coordinate across locations

Each location runs as its own organisation with its own staff, schedule, and data, while a parent organisation can connect multiple franchisees and share brand-level resources, the structure the platform needs before it can grow past one store.

Engineering Challenges

Franchise hierarchy vs. tenant isolation

Problem

The platform needed to support both an independent single store and a franchise network, without one org ever seeing another's data by default.

Decision

A self-referencing parentId relation on Organization lets a parent connect multiple franchisees and share brand-level resources, while every query is still scoped by orgId rather than relying on the UI to hide things correctly.

Result

One data model supports both a single independent location and a multi-location franchise, with tenant boundaries that don't depend on the interface behaving correctly.

Role-based access at org scale

Problem

Owners, managers, and staff need different tools from the same system, and permission logic scattered across screens is exactly where multi-tenant bugs hide.

Decision

Permissions are modelled as org-scoped Role → Permission → MemberRole join tables, checked centrally in a shared authz layer rather than per-page.

Result

Each role only sees the tools relevant to its job, and permission checks are covered directly by the largest slice of the test suite (151 server-action tests) instead of being trusted to the UI.

Making overlapping schedules readable

Problem

Once multiple people, frequencies, and roles overlap on one timetable, five stacked task cards in the same slot become unreadable on a phone mid-shift.

Decision

I introduced grouped timetable cards so overlapping entries render as one group that expands into individual items on demand, instead of exposing every entry at once.

Result

A tired staff member can glance at their phone and understand the day in seconds. Complexity is handled by the system, not passed to the user.

What I Learned

Architecture

Request Flow

Web and mobile requests enter through different transport mechanisms, but both authenticate, validate and normalise input before calling the same shared business logic.

Architecture Principle

Server Actions and API routes are transport layers, not separate implementations of the product logic. Both authenticate and validate requests before calling the same shared business logic, which then accesses organisation-scoped data. This keeps web and mobile behaviour consistent, avoids duplicated rules, and makes security and performance constraints easier to enforce.

Web and mobile use different authentication mechanisms, but both resolve into the same application logic and organisation context. This allows the two clients to share the same behaviour and data rules while presenting the information differently for desktop and mobile layouts.

  • Entry Layer: protects the application boundary and converts different client requests into clean, trusted input.
  • Business Logic: focuses on correctness and efficiency, permissions, workflow rules, and returning the right amount of data rather than HTTP/API details.
  • Data Access: ensures database queries only access the correct organisation’s data, return a limited amount of data, and keep reads and writes controlled.

Frontend Architecture

Each page acts as the main coordinator for its feature. It loads the primary data needed for the initial render on the server, then passes only the relevant data into smaller components responsible for presentation and interaction. When a component needs additional data after the page has loaded, such as for pagination, infinite scroll or on-demand updates, it can request that data through an API route.

Page / Server Components
  • Load the main data needed for the initial render.
  • Structure the page.
  • Pass only the relevant data into feature components.
Feature / Client Components
  • Turn that data into interactive UI.
  • Handle local interaction and presentation.
  • Can request additional data when needed.
  • Examples: pagination, infinite scroll, refreshes, on-demand requests, auth-derived UI state such as isParent.
Shared UI Components
  • Reusable navigation, sidebars, dialogs, controls and repeated UI patterns.
  • Implemented once and reused across pages.
  • Keep behaviour and styling consistent.
  • Reduce duplicated code and make future changes easier.

Design Before Implementation

Major workflows are designed in Figma before implementation. This is used to define layout, interaction and responsive behaviour, but also to identify reusable patterns and component boundaries before code is written, so components aren't created ad hoc and duplicated later.

File Storage Controls

Uploads are validated before reaching Supabase Storage so the application only accepts file types and sizes that its workflows can process reliably.

  • General image uploads: limited to supported image formats and a 5 MB maximum to keep uploads lightweight and predictable.
  • AI-assisted scan-to-task: supports additional mobile formats such as HEIC/HEIF where required, because device-generated files need explicit handling before they can be processed reliably.
  • Storage access: handled separately from relational database access, with its own validation and access rules.

Multi-Tenant Model

Franchise hierarchy

Organizations connect directly with their parent/child Organizations, so a franchisee stays independent while a parent can connect and manage multiple locations.

Access control

Access flows from Membership to MemberRole to Role to Permission, all scoped to one Organization, so access never crosses tenant boundaries.

Org-scoped resources

Tasks, timetables, rosters, tools, and menus each carry an orgId, so every query is scoped at the data layer, not the UI.

Data model

55 Prisma data models covering auth, organisations, tasks, scheduling, rostering, tools, menus, comments, and admin/audit data.
