Overview

Project Overview

FriendChise Mobile brings FriendChise's operational knowledge and task workflows directly to staff working on the floor. Instead of adapting the desktop management experience to a smaller screen, the app focuses on quick access to tasks, recipes, procedures, and workplace knowledge during a shift.

The goal is to reduce the number of interactions required to find or record information, while making native mobile capabilities, such as the camera, part of everyday operational workflows.

Why Mobile?

The web platform is better suited to planning, administration, scheduling, and managing operations from a larger screen. Mobile serves a different environment: staff may be moving around the store, checking a recipe mid-task, working with one hand, or capturing information directly from the physical workplace.

This led to a separate mobile experience built around shorter interactions, persistent state, higher information visibility, and native device capabilities, rather than simply reproducing the desktop interface.

Workflows

Feed-style task list

Need

Staff need to understand tasks quickly while working without repeatedly opening detail pages.

Approach

Descriptions and important details are surfaced directly in the task list, making it behave more like an information feed.

Benefit

Staff can scan and act on tasks with fewer taps and less navigation during a shift.

Context-preserving interactions

Need

Mobile work happens in short bursts, and staff should not lose their place every time they return to the app.

Approach

The app remembers where the user left off, and in selected workflows the keyboard dismisses after inactivity so screen space returns to the task, recipe, or procedure being viewed.

Benefit

The interface stays focused on the content, reducing interaction friction on a constrained mobile viewport.

Camera-assisted knowledge capture

Need

Printed procedures, recipes, documents, and other operational material still need to become structured knowledge inside FriendChise.

Approach

Staff can photograph that material and pass it through Scan-to-Task, which extracts the information into a task draft or knowledge entry.

Benefit

Useful operational information can be captured on the floor and fed back into FriendChise without switching to a desktop workflow.

Architecture

System Overview

FriendChise Mobile is a separate native client built on the same backend, organisation model, permissions, and business rules as the web application. The mobile layer focuses on native interaction and smaller-screen workflows without duplicating core application logic.

Shared Backend

The mobile app is a different client, not a separate product backend. It consumes the same core application rules and organisation-scoped data as the web application, while presenting those workflows in a form better suited to frontline mobile use.

  • Mobile and web share the same organisations, users, tasks, procedures, and business rules
  • The mobile app does not implement a separate version of the core product logic
  • Differences are mainly in presentation, interaction, and native capabilities

Authentication

Web sessions and mobile requests reach the backend differently but resolve to the same place. The web client uses session-based authentication, while mobile uses a bearer token issued after OAuth. Both resolve to the same backend user, membership, and organisation context, so the same permissions and business rules apply regardless of which client made the request.

Mobile OAuth → Bearer token → Shared backend authorization context

Client State & Data

Server data is fetched and cached through a query layer, so screens request only the data they need rather than loading the entire product state up front. Local component state handles interactions specific to a screen, and the session is persisted securely on-device between launches. When data goes stale or the app reconnects, the affected screens refetch rather than trusting an old snapshot.

Native Integrations

Native device concerns are handled by the mobile client, while validation, permissions, and product rules remain shared with the backend.

  • Camera access and photo/document capture
  • Document and file selection for uploads
  • Deep linking and OAuth handoff back into the app
  • Native secure storage for session persistence

Engineering Challenges

OAuth handoff on a native app

Problem

A plain browser tab can lose the "user activated" state across Google's multi-hop redirect chain, so the final redirect back into the app sometimes renders as a web page instead of returning control to it.

Decision

Use ASWebAuthenticationSession (via expo-web-browser) instead of a Linking-based browser tab, with an attempt-ID guard so a stale OAuth attempt can't resolve after a newer one has started.

Result

Google and LinkedIn sign-in hand off back to the app reliably, including when a user restarts the flow mid-attempt.

HEIC compatibility in the scan pipeline

Problem

iPhone photos (especially Portrait/Live/Burst shots) save as HEIC with embedded auxiliary images, and some variants aren't reliably decoded by the backend's processing pipeline.

Decision

Re-encode HEIC/HEIF to JPEG on-device with expo-image-manipulator before upload, and fall back to extension-based MIME detection for ambiguous file types.

Result

The backend only ever receives a format its processing pipeline can handle.

Synchronising mobile session expiry

Problem

The mobile session is a signed server token the client has no reason to decode, so the app needs another way to know when to sign the user out.

Decision

The OAuth callback supplies an expiresAt timestamp separately, stored alongside the token in the auth store, and a session watcher schedules a single timer to clear the session at that boundary.

Result

Session state stays consistent with the server-issued token's lifetime without any client-side token decoding.

Network resilience on mobile connections

Problem

Uploads and scan requests can hang or get abandoned mid-flow on a spotty store Wi-Fi connection, and large files waste time if they're rejected only after a slow upload finishes.

Decision

Data requests go through a shared authenticated fetch wrapper with a distinct AbortController reason for timeouts versus user cancellation, and Scan-to-Task checks the 15MB size cap on-device before any upload starts.

Result

Failures surface a specific, actionable message instead of a generic network error, and oversized files never leave the device.

Product Impact

Production Usage

The app started on a shared device at Walker's Doughnuts via TestFlight and is now live on the App Store. Task creation and Scan-to-Task moved off paper and photo message threads into a task list staff already recognize from the web platform, so the record of what got done stays in one place instead of split across a phone's camera roll and a chat thread.

Per-staff installs are rolling out now that the App Store listing is public, replacing the single shared device.
