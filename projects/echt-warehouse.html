Overview

How the Project Started

The project started after I heard repeated frustration about having to check three different WMS tables to confirm inventory information. Experienced staff knew which values to compare and where to look, but the process was difficult for newer staff to learn and easy to get wrong.

I translated that operational problem into a technical specification for the WMS software developer. I mapped how the three tables related, identified the fields and calculations needed from each, defined filtering and edge-case behaviour, and described how they should be combined into one reliable operational view.

From Operational Problem to Technical Design

  • Understand the data: traced how fields across three WMS tables related and which values depended on one another.
  • Define the logic: specified the calculations, filters and edge cases required for a reliable combined view.
  • Translate requirements: turned warehouse staff needs into implementation requirements the WMS developer could build from.

The Problem

Translating Operational Needs

Staff could describe the warehouse problem, but the software needed precise rules for what data mattered, how the fields related, what should be calculated, and what should appear in the final view.

Understanding the Data Relationships

I had to identify which fields across the three WMS tables affected replenishment accuracy and efficiency, how those values depended on one another, and which calculations, filters and edge cases were required for a reliable combined view.

Delivering on Time

The solution needed to be defined, implemented and checked within roughly one week before the Christmas peak. That made it important to keep the requirements clear, validate the calculations carefully, and make sure the new view was reliable before staff depended on it.

DEBUGGING & PROBLEM SOLVING

Missing Replenishment Items

After the new report went live, some items that still needed to be replenished were present in the old report but missing from the new combined view.

1. Contained the Issue

I asked staff to stop relying on the new report and return to the existing report while the issue was investigated.

2. Compared Expected vs. Actual Output

I used the old report as the reference point and compared it against the new view, collecting rows that were missing or returning incorrect values.

3. Escalated Early

Once I confirmed the issue was repeatable, I contacted the WMS software developer immediately rather than waiting until I knew the exact cause.

4. Investigated Possible Causes

Without access to the underlying implementation, I considered several possibilities, including incorrect implementation of the specified logic, missing data inputs, or incorrect handling of calculated values.

5. Looked for Patterns

While waiting for a response, I compared affected and unaffected rows, looking for repeated values, unusual fields, or any common characteristic that could explain the failures.

6. Found a Useful Clue

The strongest pattern was that the missing rows shared the same date. I passed that observation to the software developer as a possible clue that the report was not recalculating correctly as the source data changed.

7. Developer Confirmed the Issue

The software developer used that information during their investigation and identified the implementation issue.

Technical Design

Selecting the Relevant Data

I reviewed the available WMS reports to determine which data was actually needed for replenishment. Some information overlapped across reports, so I narrowed the workflow down to three main tables and identified the fields required for the combined view.

Defining the Combined View

I mapped the relationships between those fields, defined new calculated values where the existing reports did not provide what staff needed, and specified which information should appear in the final operational view.

Setting Clear Rules Before Implementation

Before implementation, I documented the calculations, filtering behaviour, edge cases and expected outputs so the WMS software developer had clear rules to build and validate against.

For example, stock already moved into replenishment locations should reduce the remaining quantity shown to staff, and rows with nothing left to replenish should no longer appear in the view.

IMPACT & OUTCOMES

Goal

The goal was to turn three separate WMS views into one reliable replenishment workflow, making customer-item retrieval faster and more accurate while reducing a process that typically required both a computer operator and forklift operator into something one person could coordinate.

Why Accuracy Mattered

Replenishment errors could leave pick locations empty, preventing pickers and packers from completing customer orders. Missed items created backlog for the following day, and mistakes late in the week could carry into Monday because the warehouse did not operate over the weekend.

During the Christmas peak, this could increase labour pressure, require additional casual staff, delay orders, and pull experienced staff away from other warehouse work.

Operational Outcome

  • 3 reports → 1 operational view — reduced the need to cross-check multiple WMS screens.
  • Less manual checking — staff could make replenishment decisions from one place.
  • One-person coordination — work previously split between computer and forklift workflows could be coordinated by one operator.
  • More flexible staffing — experienced staff could spend more time on picking, packing, receiving inventory, and other peak-period work.

Estimated Outcomes

  • 60–80% faster retrieval — less time spent confirming inventory across multiple reports.
  • ~50% faster onboarding — fewer reports and workflow rules for new staff to learn.
  • ~40% fewer errors — less repeated cross-checking and inconsistent interpretation between views.

What Happened After Launch

The initial deployment exposed a stale-data issue that caused some required replenishment items to disappear from the new report. I helped contain the issue, compared the old and new outputs, identified a useful pattern in the affected rows, and passed that evidence to the WMS software developer for investigation and correction.
