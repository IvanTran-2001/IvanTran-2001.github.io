Summary

Building FriendChise required more than adding features. I had to solve complex UI state problems, simplify overlapping timetable data, design a franchise hierarchy, and turn staff feedback into practical product decisions.

The project also changed how I approach engineering. I now spend more time understanding data flow, component boundaries and user needs before implementing a solution.

Managing Shared UI State

The ActionSidebar was one of the hardest technical parts of FriendChise.

It needed to display different content depending on the user’s current action, including grouped timetable cards and conversion-list workflows. The difficulty was that the sidebar could remain open while the underlying data changed, leaving the rendered content tied to an older snapshot.

My first solution was to reopen the ActionSidebar with updated content, effectively replacing what was already inside it. That worked, but it became clear that a controlled re-render function was a cleaner and more reusable approach.

This challenge improved my understanding of React rendering, snapshots, component trees and shared state. It also taught me that when one interface element depends on many parts of the application, state ownership needs to be designed deliberately.

Simplifying Overlapping Timetable Data

The timetable became difficult to read when several tasks occupied the same time period.

Displaying five separate task cards in the same space created visual clutter and made editing or moving items harder. I introduced grouped timetable cards so overlapping entries could be represented as one readable group, while still allowing users to open the group and manage each item individually.

This taught me that complexity should be handled by the system rather than passed to the user. When an interface needs lengthy instructions, it usually means the design still needs work.

The same principle influenced the conversion-list workflow. I focused on reducing the number of visible decisions and making the next action clear instead of exposing every internal rule at once.

Designing a Franchise Hierarchy

FriendChise needed to support both independent workplaces and larger franchise networks.

Each franchisee operates as its own organisation, with its own staff, schedules, tasks and local data. A parent organisation can also connect multiple franchisees through a parentId relationship.

When a new franchisee joins a network, it can inherit shared resources and brand settings from the parent organisation, including items such as logos, tasks, procedures and operational knowledge. At the same time, each franchisee keeps control over its own local workflows and can share selected information with other locations.

The permissions model reflects this structure. A franchise parent can manage or govern connected franchisees, while each franchisee remains an independent tenant with its own access boundaries.

This was one of the most important architectural lessons in the project. Multi-tenant design is not only about separating data. It is also about deciding what should be inherited, what should remain local and who has authority at each level.

Building From Real Workplace Feedback

Many FriendChise features came directly from staff frustrations.

One staff member wanted to replace paper-based processes. Another wanted a fairer way to distribute work because some employees were repeatedly assigned tasks that others did not know how to complete. Another suggested a camera system that could count doughnuts automatically and update inventory data.

Not every idea became an immediate feature, but each one helped shape the product direction.

These conversations taught me to separate the underlying problem from the proposed solution. A request for a camera system is not only about computer vision; it reflects a need for faster and more accurate stock tracking. Complaints about unfair work distribution point to gaps in training, visibility and task allocation.

This changed how I gather requirements. I now focus first on the operational problem, then decide whether the best response is a new feature, a simpler workflow or clearer information.

Limiting Data to the User’s Working Context

FriendChise avoids loading unlimited timetable data at once.

The application fetches timetable entries within a defined date range, currently limited to a maximum span of one week. This matches how staff use the system and prevents the client from requesting an unnecessarily large amount of data.

A normal workplace is unlikely to contain more than 1,000 tasks in a single week, but the architecture still needs sensible boundaries. Restricting requests by organisation and date range makes the system more predictable and provides a base for adding pagination or stricter limits later if usage grows.

This taught me that scalability often begins with simple decisions: fetch only what the current screen needs, scope every request correctly and avoid assuming that all data should be loaded at once.

What I Would Do Differently

I would make FriendChise open source earlier.

Working with contributors exposed me to different approaches, unfamiliar mistakes and edge cases I would not have encountered alone. Reviewing their work also forced me to understand the codebase more deeply and communicate requirements more precisely.

I also learned to spend more time reading before building. Understanding the existing data flow, component structure and ownership boundaries is usually faster than implementing immediately and correcting the design later.

FriendChise taught me that strong software development depends as much on reading, architecture and communication as it does on writing code.
